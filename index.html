Run every command of Storing and Retrieving Data from HDFS and NoSQL Databases here. The terminal answers as your VM would, and the right side shows what each command did: HDFS blocks on the DataNode, MongoDB scanning or using an index, and HBase rows sorted by their key.

HDFS

Unit: a file, cut into 128 MB blocks
Good at
Full scans, cheap bulk storage
Bad at
Small files, random access, updates
Schema
None; the reader imposes it

MongoDB

Unit: a document
Good at
Flexible nested records, rich queries
Bad at
Very large scans, huge write throughput
Schema
Per document

HBase

Unit: a cell (row, family, qualifier, version)
Good at
Random read or write of one row at huge scale
Bad at
Anything but a row-key lookup or range
Schema
Families fixed, qualifiers free

The question that decides between them is never "which is best" but "what is the access pattern?"

What this lab teaches

    

      

        
    
          
  1. Storage design decides query cost. The same question took tens of seconds on HDFS, milliseconds on MongoDB with an index, and milliseconds on HBase. Each number follows from how the store lays out data: HDFS scans, MongoDB walks an index, HBase jumps to a key range.
    2. 
          
  2. HDFS is files cut into blocks. The NameNode keeps only metadata (which blocks make up which file, and where they live); the DataNode keeps the blocks as ordinary files on its disk. fsck shows the mapping. Renames are metadata-only and instant; copies move every byte.
    3. 
          
  3. HDFS is write-once. No random writes, no in-place updates. It is built for loading big files and scanning all of them.
    4. 
          
  4. Read explain() before trusting a query. COLLSCAN with 2,000,000 documents examined to return 471 means no usable index. A compound index on the filter fields turned that into an index scan that examined only the 471 matches. Field order matters: {host, event_date} cannot serve a filter on event_date alone.
    5. 
          
  5. In HBase, the row key is the design. Rows are sorted by key and split into regions by key range. A sequential key sends every write to the last region (the hotspot). A salt prefix spreads writes, the host keeps one host's history together, and a reversed timestamp puts the newest row first.
    6. 
          
  6. Spark reads all three. With the Mongo connector, Spark pushes filters down so MongoDB does the filtering, and only matching documents travel.
    7. 
          
  7. Choose by access pattern. Scan everything cheaply: HDFS. Flexible documents with ad-hoc queries: MongoDB. One key, or a key range, at huge scale and write rate: HBase.
    8. 
        

        

          
For your row key paragraph

          
Answer three questions in order. What spreads the writes across regions? (the salt, so no single region server takes every insert). What keeps the rows you read together contiguous? (the host after the salt, so one host's history is a single range scan). What order do readers want inside that range? (newest first, so the timestamp is reversed). Then name the cost: to read one host you must know its salt, which is why the salt is computed from the host rather than chosen at random.
